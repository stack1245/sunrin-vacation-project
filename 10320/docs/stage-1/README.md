# Stage 1 개발 명세

## 기본 설정

주인공은 국가의 임무를 받고 기밀 문서를 회수하러 온 국가 비밀 요원이다. 임무 장소는 폐쇄된 버려진 연구소이며, Stage 1은 플레이어가 게임 조작과 퍼즐 진행 흐름을 익히는 입문 스테이지다.

실제 플레이는 Phaser Scene으로 구현한다. 외부 그래픽 에셋 의존도를 낮추기 위해 Phaser 도형, 텍스트, 코드로 생성한 그래픽을 중심으로 사용한다. 이 문서에서 정의하는 Account & Progress 계층은 게임 렌더링이나 퍼즐 정답 판정을 담당하지 않는다.

## 진행 순서

첫 진입 흐름은 다음과 같다.

`연구소 외부 → 키카드 획득 → 입구 잠금장치 해제 → 연구소 진입 → 중앙 복도`

중앙 복도에서는 선택 카드 또는 게임 내 이동을 통해 다음 구역을 오갈 수 있다.

- 연구 자료실
- 화학 실험실
- 보안 통제실

실질적인 진행 순서는 아래 순서를 지켜야 한다.

`연구 자료실에서 화학 실험실에 필요한 정보 획득 → 화학 실험실 퍼즐 해결 → 보안 통제실에 필요한 정보 획득 → 보안 통제실 퍼즐 해결 → 기밀 문서 보관실 해금 → 기밀 문서 획득 → 연구소 외부로 탈출 → Stage 1 클리어 → Stage 2 해금`

분기 이동은 허용하되 진행 플래그는 이 선행 조건을 건너뛸 수 없다. 실제 퍼즐 정답 판정은 퍼즐 담당 코드에서 수행하고, 성공한 뒤에만 진행 브리지에 새 상태를 저장한다.

## 상태와 저장 책임

`user_stage_progress`는 스테이지 단위 상태(`locked`, `unlocked`, `in_progress`, `cleared`), 최초 시작/클리어 시각과 최고 기록을 관리한다. `user_stage_saves`는 현재 방, Stage 1 내부 진행 플래그, 누적 경과 시간과 저장 버전을 관리한다.

두 데이터의 책임을 섞지 않는다. 일반 저장은 `user_stage_saves`의 세부 상태와 `user_stage_progress.last_played_at`만 갱신하며, 진행 `status`, `cleared` 변경과 Stage 2 해금은 건드리지 않는다. 클리어와 해금은 서버의 `complete_stage_one()`만 수행하며, 저장 JSON의 `escaped` 값만으로 클리어되지는 않는다.

Stage 1 상태 타입과 선행 조건은 [progress-integration.md](./progress-integration.md)를 기준으로 한다.

## 역할별 책임 범위

### PM & Account/Progress

- Stage 1 상태와 저장 버전 명세
- 로그인 확인 및 Stage 1 접근 권한 검사
- 시작, 이어하기, 저장, 클리어 기능
- Supabase 진행도 및 세부 저장 연동
- 정상 클리어 시 Stage 2 해금
- Phaser/퍼즐 담당자가 사용할 연동 인터페이스
- 통합 테스트 및 인수 기준 관리

### 게임 플레이 담당

- Phaser Scene과 Scene 생명주기
- 캐릭터 이동 및 충돌
- 방 이동과 현재 위치 반영
- 상호작용 가능 대상 감지

### 퍼즐 담당

- 연구 자료실 암호 퍼즐
- 화학 실험실 퍼즐
- 보안 통제실 퍼즐
- 기밀 문서 보관실 최종 퍼즐
- 퍼즐 성공 시 명세된 진행 플래그만 변경

### 연출 및 QA 담당

- 화면 전환과 상호작용 안내
- 성공/실패 피드백 연출
- 효과음
- 전체 플레이 흐름과 저장 복구 테스트

## 팀원 연동 계약

- Phaser Scene은 Supabase 클라이언트나 테이블 이름을 import하지 않고 `StageOneProgressBridge`만 사용한다.
- 호출자는 `userId`, 진행도 `status`, 다음 스테이지 ID를 전달하지 않는다. 서버는 현재 Supabase 세션의 `auth.uid()`만 신뢰한다.
- 퍼즐 성공 여부는 퍼즐 담당이 판정하되, 성공 이후 상태 저장은 브리지를 통해 수행한다.
- 방 이동, 단서 획득, 퍼즐 해결, 기밀 문서 획득 직후 자동 저장을 권장한다.
- 탈출 상태 저장 뒤 `complete()`를 별도로 호출한다. `save()`는 클리어나 해금을 수행하지 않는다.
- 저장 실패는 즉시 게임 오버로 취급하지 않는다. 마지막 정상 저장 상태를 유지하고 사용자에게 재시도 경로를 제공한다.

## 통합 테스트 기준

- 비로그인 요청과 잠긴 Stage 1 요청이 거부된다.
- 접근 가능한 사용자에게 저장이 없으면 최초 `start()` 또는 `load()`에서 기본 저장을 한 번만 생성하고, `start()`는 상태를 `in_progress`로 만든다.
- 재시작/재호출 시 기존 저장 상태와 최초 시작 시각이 유지된다.
- 저장 상태의 버전, Room ID, boolean 타입, 크기, 경과 시간과 진행 선행 조건을 런타임과 DB 양쪽에서 검사한다.
- RLS 및 함수 권한으로 다른 사용자의 저장을 조회하거나 바꿀 수 없다.
- 일반 저장으로 `user_stage_progress.status` 또는 Stage 2 상태를 바꿀 수 없다.
- 서버에 저장된 상태가 기밀 문서 획득 및 탈출 조건을 모두 만족한 경우에만 클리어된다.
- 정상 클리어는 기존 최고 기록 규칙을 유지하고 다음 공개 스테이지를 해금한다.
- 중복 시작, 저장 및 클리어 호출은 데이터를 초기화하거나 최초 클리어 시각을 덮어쓰지 않는다.
- 기존 로그인/회원가입, `/stages`, 다른 스테이지의 범용 시작/클리어 흐름이 회귀하지 않는다.
- Next.js 타입 검사, ESLint, 단위 테스트와 프로덕션 빌드가 통과하며 hydration 경고와 secret 노출이 없다.

## 구현 제외 범위

이번 Account & Progress 작업에서는 Phaser 게임 화면, 캐릭터 이동/충돌, 캐릭터 이미지, 키카드 그래픽, 방 배경, 암호·화학·보안·스도쿠·TTF 퍼즐, 효과음, 애니메이션을 구현하지 않는다. 리더보드 UI, 메인 페이지, 로그인/회원가입 UI, Stage 2 플레이도 변경하지 않으며 외부 에셋이나 상태 관리 라이브러리를 추가하지 않는다.
